# Lead-capture automation plan (analysis only, no edits)

## What exists today (verified)
- Every website form (QuickEnquiryForm, PrivateYogaEnquiryForm, BookOnlineYogaForm, SmartConsultation) calls `submitLead()` in `src/lib/leads.ts`. That function inserts straight from the browser into `public.leads` using the public key. RLS allows INSERT only; there is no SELECT, UPDATE or DELETE.
- The MCP tool `submit_consultation_request` inserts with `source: "mcp"`. The insert policy only allows `website` and `website_paid_online_yoga`, so these inserts are most likely rejected today. This is a separate bug to fix.
- The only trigger on `leads` is `leads_set_updated_at`. No webhook, notification or forward exists, and the Make.com forward was retired.
- The database already has `pg_net`, `pg_cron` and `pgmq` (used for the email queue that calls a server route). That same pattern can be reused.
- There are no Telegram or Google Sheets connections in the workspace. Only GA, TikTok and Search Console are connected. Lovable has a native **Telegram connector** and a **Google Sheets connector**. Both are managed through the connector gateway, so there is no raw bot token or service-account JSON to handle.
- Caveat: `SmartConsultation` may insert partial steps (statuses `micro_commit`…`review`). Only notify on `status = 'submitted'`.

## Recommended architecture (simplest and reliable)

```text
Form -> leads INSERT (unchanged)
      -> AFTER INSERT trigger (status='submitted') -> row in lead_notifications (outbox)
      -> pg_net POST to /api/public/leads/dispatch (secret header), plus pg_cron sweep every 1 min
      -> server route: claim pending rows -> Telegram sendMessage + Sheets append/upsert
      -> mark each channel sent/failed, retry with backoff, give up after N attempts
```
- Use a TanStack server route, not a Supabase Edge Function (this is the project standard).
- The outbox table gives idempotency: one row per lead, with per-channel status columns (`telegram_status`, `sheet_status`, `whatsapp_status`), `attempts`, `last_error` and `next_attempt_at`. Claim rows with `UPDATE ... WHERE status='pending' ... FOR UPDATE SKIP LOCKED`, so parallel calls cannot double-send.
- Sheets: store `lead_id` in column A. Look it up and update if found, otherwise append. A retry then cannot create duplicate rows.
- Telegram: send only when `telegram_status != 'sent'`. Put `lead_id` in the message text.

## Implementation steps
1. Link the connectors: Telegram (create a bot with BotFather, add it to the team group, get the `chat_id`) and Google Sheets (pick a sheet with a header row).
2. Migration: create the `lead_notifications` table (grants for service_role only, RLS enabled, no public policies). Add a SECURITY DEFINER trigger on `leads` AFTER INSERT (plus AFTER UPDATE when status changes to `submitted`) that inserts the outbox row with `ON CONFLICT (lead_id) DO NOTHING` and fires `net.http_post`. Add a pg_cron sweep job.
3. Server route `src/routes/api/public/leads/dispatch.ts`: check the shared-secret header with a timing-safe compare. Load `supabaseAdmin` inside the handler. Process a batch, call the gateway for Telegram and Sheets, and update statuses.
4. Message format: name, WhatsApp as a wa.me link, email, service, goals, preferred time, market/timezone, UTM source/campaign, landing page and time. Leave health notes out of Telegram, or mark them clearly. Escape HTML.
5. Optional WhatsApp:
   - Internal alert: Telegram covers this. The WhatsApp Cloud API needs a verified Meta Business account, an approved template and a per-message cost.
   - Automatic acknowledgement to the lead: needs Meta WhatsApp Cloud API or YCloud (planned per project knowledge), an approved utility template and the lead's consent. Do this as phase 2.
6. Fix the MCP `source: "mcp"` rejection: allow `mcp` in the policy, or change the tool to use `website`.
7. QA: insert one clearly labelled test lead in preview, then check that exactly one Telegram message and one sheet row appear. Call the dispatcher again and confirm nothing is duplicated. Simulate a failure and confirm the retry. Then delete the test row.

## Required secrets
- `TELEGRAM_API_KEY`, `GOOGLE_SHEETS_API_KEY`: set automatically when the connectors are linked.
- `LOVABLE_API_KEY`: already exists.
- `LEAD_DISPATCH_SECRET`: generated by Lovable. It is stored in the vault for pg_net, and the server route compares against it.
- Config (not secret): `TELEGRAM_CHAT_ID`, `LEADS_SHEET_ID`, tab name.
- Later: `WHATSAPP_ACCESS_TOKEN` / `PHONE_NUMBER_ID` (Meta) or a YCloud key. Only the user can supply these.

## Risks
- Personal data (name, phone, health notes) goes to Telegram and Sheets. Keep the group private, keep sheet sharing restricted, and update the privacy page (it currently says data is stored only in the site database).
- pg_net calls go to the published domain. The preview and published sites share one database, so pick one dispatcher URL to avoid double processing (the outbox already guards against this).
- Spam inserts: public insert is allowed, so bots can flood Telegram. Mitigation: notify only on `submitted`, add a light length/format check, and optionally a honeypot.
- WhatsApp auto-replies need Meta template approval and opt-in, and can get the number banned if misused.
- Telegram limits bots to about 20 messages per minute per group. That is fine at current volume.
- Sheets is a mirror only. The database remains the source of truth.
